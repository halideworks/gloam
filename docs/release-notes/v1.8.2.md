A single fix, and it matters if you use night mode on an SDR display: for many SDR
setups, night mode did nothing at all. It does now.

## Fixed

**Night mode now works on SDR displays.** Windows validates every hardware gamma-ramp
write and rejects the entire write when any entry deviates more than half of full scale
from neutral. Gloam's default 2700K night setting cuts the blue channel just past that
limit on SDR displays, so Windows refused the ramp and the screen did not change at all:
no warmth, no dimming, nothing. Strong dimming on SDR could fail the same way. HDR
displays were never affected because their PQ-encoded ramps stay near neutral at the top
and pass validation.

Gloam now builds the closest ramp Windows accepts. At 2700K the difference from the
requested shift is confined to the top four entries of the blue channel: pure white lands
near 2720K instead of 2700K, and everything below white receives exactly the requested
correction. When this limiting engages, Gloam logs one line per display saying so.

If you want the full range on SDR, the Windows limit itself can be lifted with the same
registry override f.lux and ArgyllCMS document; the
[troubleshooting guide](https://github.com/halideworks/gloam/blob/main/docs/troubleshooting.md#night-mode-is-not-changing-anything)
has the exact value and key. Gloam detects the override and stops limiting.

**Measured-behavior note:** calibration math is untouched. Any ramp Windows accepted
before this release is built bit-identically, HDR output included; the only outputs that
change are ones Windows previously rejected outright, which applied nothing. No
colorimeter re-validation is required for this release for that reason. The validation
boundary itself was measured on real hardware (Windows 11 22621): the rejection of the
old 2700K SDR ramp and the acceptance of the corrected one were both confirmed against
the live API.
